# Manifests

Kubernetes definitions live in `config/kubernetes/`.

- `deploy/` is applied everywhere, **including production**. Changing anything
  here is a production change.
- `development_overrides/` is merged on top in development only. Anything that
  should not reach production belongs here.

## How the two are merged

Lists are merged by the `name` key and dictionaries by unioning their keys. Two
consequences follow, and the second one is a trap:

- An override can **add** an environment variable that `deploy/` does not set.
  So a variable needed only in development belongs in `development_overrides/`
  alone, with a sensible default in the application's own settings.
- An override that sets `value` for a variable `deploy/` defines with `valueFrom`
  produces a single entry carrying **both**, which the Kubernetes API rejects:

  ```
  spec.containers[0].env[0].valueFrom: Invalid value: "":
      may not be specified when `value` is not empty
  ```

  So a variable goes in one place or the other, never both. If you need it in
  development only, take it out of `deploy/` rather than overriding it.

## Choosing where a setting goes

Ask whether production needs it to be configurable at all. A value that will not
change, such as the production domain, is safer as a default in the
application's settings than as a manifest reference: a default cannot be moved
by editing a ConfigMap, and the deployment cannot fail because a key is missing.

## Tests and migrations

The development test database is cached between runs, so the first run after
adding a migration needs `kubeyard test --force-migrate-db`, and reverting one
is easiest with `--force-recreate-db` rather than downgrading.

How migrations are *generated* is project-specific: which tool, and whether they
are written by hand or autogenerated through `kubeyard shell`. The repository's
own `CLAUDE.md` covers that.
